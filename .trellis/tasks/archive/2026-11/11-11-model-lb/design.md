# 设计：模型层负载均衡（同一逻辑模型的多 provider 池）

## 1. 不变量与失败模式

| 不变量 | 违反时的失败模式 |
|---|---|
| **I1 一个池只有一次选择。** 从"本次尝试的候选成员"到"这次调用哪家 provider"只发生一次，就在尝试循环组装目标的地方。 | 候选过滤在 A 处、选择在 B 处，一次尝试可能选中一个刚被判定不可服务的成员，而日志无法解释。 |
| **I2 池的失败计数与熔断器是两张表。** 排除表按"池成员此刻该不该分流量"计时，熔断器按"provider 目标整体是否健康"计数。 | 一次 429 把一家 provider 的熔断器打满 300s，把所有重试预算烧在一个数字上。 |
| **I3 调用方错误不换成员。** 400/404/422 是请求本身的问题，换一家只会得到同一个答案。 | 一个格式错误的请求被重试到池里每一个成员，把一次调用放大成 N 次计费。 |
| **I4 同一请求内不重复选中。** 一次尝试失败后，该成员从本次请求的候选集里移除。 | 池里只有一个成员可用时无限重试它，`retry_budget` 失去意义。 |
| **I5 模型过滤在选中之前。** 候选集会先按"该成员能否服务本次请求解析出的物理模型"过滤。 | 把请求发给一个必然回 404 model_not_found 的成员，再把它的 404 记成调用方错误。 |
| **I6 尝试上界来自文档自己的界。** `MAX_ATTEMPTS_PER_ROUTE` 必须覆盖池大小 × `retry_budget` × `fallback` 长度。 | 熔丝截断一次合法的尝试序列，而文档从未声明过这个更小的上界。 |
| **I7 发布期物化不变量不变。** 池成员的 `base_url`、凭证、模型映射在发布时全部物化，任一失败则整份文档被拒、保 LKG。 | 发布成功但某个成员在请求期才发现不可用，错误被归咎于流量而不是配置。 |

## 2. 池住在哪

```
routes[] ─┬─ provider:  X            （单成员，今天的形状）
          └─ providers: [A, B, C]    （池，本设计）
                 │
                 ▼
        发布期：chain::compile_pool → 每个成员物化（凭证/base_url/model_map/能力）
                 │
                 ▼
        请求期：每次尝试
                 │
                 ├─ 候选 = 池成员 ∩ 未尝试过 ∩ 模型可服务 ∩ 未被排除 ∩ 熔断器闭合
                 ├─ 选择（weighted_random | round_robin）
                 ├─ 调用
                 └─ 结果分类 → 是否消耗 retry_budget / 是否换成员 / 是否记入排除表
```

插入点仍在 `nico-server::llm` 的计划编译与尝试循环，**不进 `nico-http`**：那里不依赖 `nico-llm`，provider 语义反向流入的接缝已经存在（`Destination` + 字节级 body seam）。

## 3. 配置模型

`nico-core` 的 `Route` 增加池面：

```rust
pub struct Route {
    // ... 既有字段
    target: RouteTarget,            // Provider(name) | Upstream(name) —— 二者互斥的现有表达
    providers: Option<Pool>,        // 新增：池成员，与 target 互斥
}

pub struct Pool {
    members: Arc<[PoolMember]>,
    strategy: PoolStrategy,         // WeightedRandom（默认）| RoundRobin
}
pub struct PoolMember {
    name: Arc<str>,                 // 指向已声明的 provider
    weight: u16,                    // 0..=1000，缺省 1；0 = 不参与分发
}
```

- `providers` 与 `provider` 互斥，两者都写或都不写都在发布期被拒（与 `upstream`/`provider` 互斥同一处理方式）。
- `weight: 0` 的语义是**不参与分发**，只在显式指名（`fallback` 成员）时被使用。这与流量层"0 权重非法"的差别来自领域：流量层没有兜底概念，模型层有。
- 成员名必须在 `providers` 里已声明，且不得重复。
- 池大小上限：`schema_bounds` 新增 `max_pool_members`（默认 8），与 routes/upstreams/plugins 同样的有界字段做法。
- `strategy` 是**独立于流量层 `Strategy` 的枚举**：两者今天恰好共享 `round_robin`，但流量层的 `least_conn`/`ip_hash` 在模型层没有意义（没有连接、没有持续的客户端地址语义），而模型层需要的 `weighted_random` 流量层没有。共用一个枚举会逼出一个两边都含废变体的类型。

## 4. 期望的选择

`weighted_random` 是默认，也是 bifrost 唯一实际使用的分配算法。它有两个必须钉住的性质：

- **成员数量变化时不漂移。** 按累计权重区间取随机数，成员增删只改变落在新区间里的样本，而不是把所有键重新洗一遍。
- **可确定性测试。** 随机源通过一个窄接口注入：

```rust
pub(crate) trait Source {
    /// Returns a value in `0..total`.
    fn below(&self, total: u64) -> u64;
}
```

生产实现用进程内派生的伪随机（不新增 crate 依赖：仓库当前没有随机依赖，而引入一个只为这一处服务的 crate 不值得）；测试实现返回固定序列。`weight: 0` 的成员不进入权重区间，因此**结构上**不可能被选中，不依赖实现记得跳过它。

`round_robin` 按池内顺序轮转，位置跨发布保留，与流量层同一语义。

## 5. 失败分类决定处置

这是本设计的核心表。分类原料已存在：`CanonicalError` 带稳定 code、HTTP 状态与 `retryable`。

| 失败 | 识别 | 消耗 `retry_budget` | 成员处置 |
|---|---|---|---|
| 429 限流 | 状态 429（canonical `upstream_rate_limited`） | **否** | 立刻换成员；该成员进入短冷却 |
| 401 / 403 凭证或配额 | 状态 401/403 | **否** | 立刻换成员；该成员进入长冷却 |
| 5xx | canonical `retryable` | 是 | 换成员；熔断器照常计数 |
| 本地连接失败 / 超时 | 既有 `FailureStage` | 是 | 换成员；熔断器照常计数 |
| 400 / 404 / 422 | 以上都不是 | — | **不换成员**，直接作答 |

- 短冷却 10s、长冷却 300s 是**失败类别的属性，不是部署参数**，因此是常量而不是文档字段。一个需要调这些值的部署问题应该改熔断器的 `cooldown_ms`。
- 冷却到期后该成员回到候选集，不设半开探针：池成员不是连接目标，401 比连接失败更可能是配置错误，用一个真实请求去试探它反而是把错误成本转给用户。这与流量层的剔除机刻意不同，理由写在 §9。
- **排除表是进程级的**（`ExclusionTable`，与熔断器同住在 `SharedServices`）：一次请求发现 429 之后，下一次请求不再抽到该成员。键是 `(route, provider)` 而不是 `TargetIdentity`——同一个 provider 在一条路由里是池成员、在另一条里可能不是，把它全局退休会把一条路由的限流放大成整站故障。过期条目在读取时丢弃，发布时另做一次 `sweep` 防止长期驻留。

## 6. 与既有熔断器的关系

两张表，**并列不合并**：

| | 排除表（本设计） | 熔断器（既有） |
|---|---|---|
| 身份 | 池成员 | provider 目标 |
| 触发 | 429 / 401 / 403 | 连续失败达 `failure_threshold` |
| 冷却 | 按类别固定（10s / 300s） | 文档的 `cooldown_ms` |
| 作用 | 本次请求的下一次尝试不再选它 | 关闭该目标，任何请求都不再调用 |

**互不污染**：一个成员被 429 排除时，不向熔断器报告失败。这需要 `CanonicalError` 的分类结果在尝试循环里先行一步，决定"这是调用方错误 / 限流 / 目标故障"三者之一，只有第三者才落到熔断器。

## 7. 尝试预算与熔丝

```
MAX_ATTEMPTS_PER_ROUTE = MAX_RETRY_BUDGET × max(1, max_pool_members) × (1 + MAX_FALLBACK_MEMBERS)
```

- `retry_budget` 语义不变：它是**单个成员吸收的尝试次数**，不是整条路由的次数。池的存在不改变它，只改变它作用在谁身上。
- 被 429/401/403 排除的尝试不消耗预算（§5），所以实际尝试数的上界仍是"预算 × 成员数"的有限值。
- 常量因此从 `MAX_RETRY_BUDGET * (1 + MAX_FALLBACK_MEMBERS)` 变成三元乘积。**这个值只用于给尝试循环定容，不放进文档**，与今天的做法一致。

## 7.1 首字节预算（M2）

`routes[].ttft_timeout_ms` 通过 peer 的 `read_timeout` 实现，而不是独立计时器。这是被框架约束决定的，
不是偏好：

- Pingora 在会话建立时把 `peer.options.read_timeout` 写到 `client_session` 上，之后**每一次读**都用它
  （响应头与每个 body 分片）。没有"只作用于第一次读"的入口。
- `upstream_peer` 在请求体解码之前运行，所以首轮无法知道请求是否流式。若按"流式才生效"门控，最需要
  这个预算的首轮（遇到静默成员）反而不生效。

因此该字段的语义是**"这个路由的一次读最多等多久"**，流式与非流式同样适用：

| 情形 | 结果 |
|---|---|
| 成员静默（永不回头） | 预算到点，读超时 → 该成员失败 → 切下一个（e2e 覆盖） |
| 成员在预算内作答 | 不受影响，缓冲与流式皆然 |
| 成员比预算慢 | 被截断。这是代价：字段名承诺的是"首字节"，实际管的是"每一次读" |

读超时默认被当作**请求自身预算**而不重试（那是"整个请求没时间了"的语义）。有本字段时它被重新归类为
**成员失败**——判据是这次尝试是否携带首字节预算（`attempt_has_first_byte_budget`）。没有这个区分，
静默成员的超时会走"请求超时"路径，永远不会换成员。

## 8. 可观测性

- 日志：复用 `llm.target`（实际服务的成员名）、`llm.attempt`、`llm.outcome`；新增 `llm.pool`（池名 = 路由 id）与 `llm.excluded`（`rate_limited` / `credential`）。
- 指标：`gateway_llm_pool_selected_total{route_id, provider}`、`gateway_llm_pool_excluded_total{route_id, provider, reason}`。标签取文档里的名字，基数由配置决定，不随请求增长。
- 请求记录里 `llm.provider` 仍是实际服务方，池只补充"为什么不是别人"（`llm.excluded`）。

## 9. 备选方案与取舍

| 备选 | 为什么不做 |
|---|---|
| **复用流量层的 `Strategy` 枚举** | 两边的策略集只交集一个 `round_robin`。共用会得到四个变体里两个在各自领域无意义的类型，且 `build` 的穷尽 match 会被迫处理不可能的组合。 |
| **复用流量层的 `Ejection` 剔除机** | 它的半开探针语义对连接目标是正确的，对 provider 不是：用真实用户请求去试探一个 401 的成员，等于把凭证错误成本转给用户。两边的冷却单位也不同（毫秒档 vs 类别档）。 |
| **池成员也做发布期能力交集**（PRD 早期写法） | 会挡掉合法部署：一个池里各成员支持的模型集不同是常态，请求期查表更准确且无 I/O。 |
| **排除表合并进熔断器** | 违反 I2；一次 429 会打满 300s 熔断。 |
| **引入 `rand` crate** | 只为一处选择服务，而 `Source` 接口本来就需要（确定性测试）；伪随机源 10 行。 |
| **`weight: 0` 表示"已禁用"** | 与"不参与分发"混淆。本设计只接受前者语义，并让 `fallback` 显式指名成为唯一的绕过方式。 |
| **把池建在 `nico-http`** | 那里不依赖 `nico-llm`，且不认识 provider；池属于模型语义，必须与物化链路同侧。 |

## 10. 兼容性与回滚

- 文档兼容：不写 `providers` 的文档与今天等价（单成员，`providers` 缺席即旧路径）。所有既有 LLM e2e 零改动。
- 行为兼容：单成员池不经过池的选择器（与流量层的单成员短路同一做法），`weighted_random` 在只有一个成员时恒选它。
- `MAX_ATTEMPTS_PER_ROUTE` 变大是**放宽**，不拒绝任何今天合法的文档。
- 回滚形状：改动集中在 `nico-core` 的 `Route`/`RawRoute` + 池校验、`nico-server::llm` 的池编译与尝试循环分类。回滚 = 删掉 `providers` 分支与排除表，保留单 `provider` 路径，无数据迁移。

## 11. 测试策略

| 层 | 内容 |
|---|---|
| 配置单测 | `providers`/`provider` 互斥（两种错法各自的错误信息）；成员未声明；权重边界；池上限 |
| 选择单测 | `weighted_random` 的分布（注入确定性 `Source`，`3:1` 比例落在容差内）；`weight: 0` 永不被分发选中；`round_robin` 顺序；同请求不重复选中 |
| 分类单测 | 五类失败各自的处置：429 不消耗预算且换成员、401/403 长冷却、5xx 消耗预算、400/404/422 只调用一次（有断言证明上游只被调用一次） |
| 表隔离单测 | 成员被 429 排除后，其熔断器连续失败计数不增加 |
| 模型过滤 | 只有部分成员可服务请求模型时其余不被选中；全部不可服务 → `403 model_not_allowed` 且不进 `fallback` |
| 熔丝单测 | 池 3 + `retry_budget: 2` + `fallback` 2：`MAX_ATTEMPTS_PER_ROUTE` 覆盖全部尝试，无路由能越过它 |
| 集成 e2e | 三成员池，杀掉一个 → 请求仍成功；429 成员被排除且不污染熔断器；`fallback` 仅在池耗尽后发生 |
| 回归 | 单 `provider` 路由的既有 e2e 全部零改动通过；`traffic` 角色（不含 `nico-llm`）仍能编译，池配置在发布期被拒 |
